This skill is generated by project-setup from `agent-skills.config.js`. Do not edit it here: `pnpm skills:check` fails on any change, and `pnpm skills:sync` writes it again.

A pull request is ready when its tests, implementation, and comments are each the simplest that cover the intended behaviour. You can open a draft earlier. Finishing means making the pull request ready for review.

## Workflow

Run each step in a subagent with a fresh context when you can. Otherwise run it yourself. Give each step the task context and the results of the earlier steps, so that it can check its gate.

1. Keep the tests focused. Read [effect-tests](../effect-tests/SKILL.md). Cover each intended behaviour once, in the existing test file for the module. When the change needs no tests, record why.
   Continue when removing any remaining test case would leave intended behaviour uncovered, or no tests are needed.
2. Simplify the implementation. With the tests passing, look for a simpler or more idiomatic version. Reuse helpers and patterns from nearby code and from [effect-code](../effect-code/SKILL.md). Remove debugging code, temporary code, and changes that the task does not need.
   Continue when the targeted tests pass and the task needs every hunk of the diff from the merge base.
3. Review the full diff from the merge base as a maintainer would. Check correctness, failure and interruption paths, resource cleanup, names and API shape against neighbouring modules, and documentation. Fix each finding and review again.
   Continue when a review pass has no findings.
4. Clean up the comments. Remove comments that repeat the code or describe the change. Keep the rest short and about why.
   Continue when every comment explains only what the code cannot show.
5. Run `pnpm pre-push`. It runs the same checks as the `pre-push` git hook. Fix the failures that the change causes. If a fix changes the diff, repeat the steps it affects.
   Continue when `pnpm pre-push` passes, or each check that cannot run is recorded with what blocks it.
6. Open or update the pull request. The title is a short imperative summary. The description gives the problem, the decisions a reviewer needs to know, and `Closes #<issue>` for each GitHub issue the change resolves. Do not walk through the diff. Mark the pull request ready for review.
   Continue when the final changes are pushed, the description matches the final diff, and the pull request is ready for review.

The task is complete when each step's gate holds, validation passed or was reported as not runnable with reasons, and the pull request is ready for review with a description that matches the final diff.
