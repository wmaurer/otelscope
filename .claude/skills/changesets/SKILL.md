This skill is generated by project-setup from `agent-skills.config.js`. Do not edit it here: `pnpm skills:check` fails on any change, and `pnpm skills:sync` writes it again.

A changeset is the release note for the complete PR, not a log of the work. Write it after the implementation and the focused validation are complete.

If the workspace has no `.changeset/config.json`, this skill adds Changesets. Run `pnpm add -Dw @changesets/cli`. Then ask the user to run `pnpm changeset init`: it asks about the changelog, publishing access, and the base branch, which are the user's decisions.

## Workflow

1. Read the complete diff from the merge base, including any changeset that the PR already has. Name each published package that the diff changes directly. Leave out unrelated changes in the working tree.
2. Classify the impact on types, runtime behavior, entry points, required services, lifecycle, and persisted or wire data.
3. Do the breaking audit below.
4. Record why no changeset is needed, or update the PR's changeset. Create one only when the PR has none. To write it, read [authoring.md](authoring.md).
5. Check the package names, the frontmatter, the bump, and the description. `pnpm changeset status --since <base>` prints the bump that each package will get.

Keep one changeset file per PR. One file can name several packages and sum up several related fixes or additions. Later commits in the same PR update that file. Use separate files only when a maintainer asks for them, or when the PR has independent changes that need separate release notes.

## When a changeset is needed

Write a changeset for a change in observable runtime behavior, bug fixes included. Also write one for a change to an exported value or a public type; an entry point or the `exports` map; required services, errors, ownership, defaults, or lifecycle; and persisted, serialized, protocol, or wire formats.

Tests, behavior-preserving refactors, documentation, and unpublished tooling usually need none. When you are not sure, read the exports and the declarations that a consumer sees. The location of the source file does not decide it.

## Breaking audit

A change is breaking when valid existing consumer code, configuration, or data must change to keep compiling or to keep its previous behavior. Check each of these:

- **Names and locations.** Exports, entry points, and module paths.
- **Calls.** Parameters, accepted inputs, overload resolution, generic parameters, and defaults.
- **Results.** Return and error types, narrowing, members, inference, and required services.
- **Runtime contracts.** Defaults, failures, interruption, concurrency, ordering, resource lifetime, acquisition, cleanup, and mutation.
- **Data.** Persisted schemas, encodings, database layouts, protocols, and wire formats.

New exports, new optional parameters, and behavior-preserving implementations are usually not breaking. A fix that restores the documented contract is usually not breaking, but it still needs a changeset when a consumer can notice it. When overload order, structural assignability, or inference makes compatibility unclear, compile representative existing calls against the change.

The task is complete when every affected contract and published package is accounted for, and either the no-changeset decision is explicit or the PR has one valid changeset. Its release note is one sentence of consumer impact, plus migration steps for each break, with no implementation detail.
