## `effect` is a peer

A library declares `effect` in `peerDependencies` and again in `devDependencies`, and never in `dependencies`. The library and the code that uses it must share one copy of `effect`. With `effect` in `dependencies`, a consumer can install two copies: one for the library and one for its own code. The same rule holds for each `@effect/*` package whose types or services appear in the library's API.

The peer range states the versions that the library supports, for example `^4.0.0`. The devDependency is the version that the workspace builds and tests against, the same one the other packages use. A newer tested version does not narrow the peer range.

## Roles

Give each entry exactly one role:

| Role                                     | Use when                                                                                   | Completion check                                                                    |
| ---------------------------------------- | ------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------- |
| `dependencies`                           | The library's runtime code needs its own installed copy.                                   | A consumer that installs the library gets it without declaring it.                  |
| `peerDependencies`                       | Consumers provide a compatible shared package, or the library's API works with their copy. | The range states the supported consumer versions, and a dev entry exists.           |
| `devDependencies`                        | Only the build, tests, type tests, or code generation need it.                             | The runtime code and the published declarations do not need it.                     |
| `optionalDependencies`                   | A runtime feature handles its absence, and a failed install must not block the library.    | Focused tests cover the behavior with and without it.                               |
| Optional peer via `peerDependenciesMeta` | A consumer-provided integration is truly optional.                                         | It stays in `peerDependencies`, and the code loads it only when a consumer uses it. |

## Workflow

1. Read the closest package in `packages/` with the same integration shape. Classify each entry by the table. Add only what this package's runtime code, declarations, build, or tests use directly, even when a neighbor declares more.
2. Use `workspace:^` for a workspace package, unless the neighboring packages use another form. Take the versions of external packages from the packages that already use them in the same way.
3. Run `pnpm install` at the root. Read the warnings, and read the package's importer in `pnpm-lock.yaml` for the specifiers and resolutions that you intended.
4. `pnpm install` lists each new dependency whose install script it did not run. An allowed script runs third-party code on every install, so ask the user before you allow one. `pnpm approve-builds` records the answer.

The task is complete when each changed entry has one justified role, `effect` and the shared `@effect/*` packages are peers with a dev entry, each peer range states the supported versions, the lockfile importer agrees with the manifest, and each install script has an explicit decision.
