## Public and internal

`export` in the source does not mean public. Check for `/** @internal */` above the symbol. The published `.d.ts` files leave internal symbols out, but the runtime code keeps them. So when `tsc` says a name does not exist on a module whose source exports it, this is the likely reason. Do not cast and do not use `@ts-ignore`. Read the definition and write the same logic with public APIs.

## Module paths

The module paths are the keys of `exports` in `effect/package.json`. Effect v4 material written before the 4.0 release uses `effect/unstable/...` paths. In the stable release each of those modules is one level up, for example `effect/process`, and a path that contains `unstable` does not resolve.

## Option types

Write an options type inline in the signature. Mark each field `readonly`. Add `| undefined` to each optional field. `tsconfig.base.json` sets `exactOptionalPropertyTypes`, so without `| undefined` a caller cannot pass `undefined`.

```ts
export const make = (options: {
    readonly capacity: number;
    readonly strategy?: "dropping" | "sliding" | undefined;
}): Effect.Effect<Queue.Queue<number>> => ...
```

Declare a named options type only in these cases:

- Several APIs share a large set of options, and one type keeps them the same.
- The type needs conditional or mapped types that depend on type parameters.

A long option list for one API is not a reason for a named type.
